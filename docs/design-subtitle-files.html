Subtitle files

One model for subtitles inside a video and subtitles beside it. Covers issues #36 and #83, PRs #45 and #84. Version 3: every rule now points at the test, tool or source reading that backs it, and the ones nothing backs yet say so.

The idea in one sentence. A subtitle is a subtitle. Whether it sits inside the container or beside it as a file is a property, and the profile says where text subtitles belong. The profile's language rules keep running untouched; the only new work is deciding, per kept subtitle, whether it has to move.

1. Why

Bazarr and most players list a language twice when it is both embedded and present as a sidecar. People resolve that in two opposite directions: mux the file in (#36, PR #45) or move the track out (#83, PR #84). Both need the same naming convention, parser, scanner support and place in the profile. Built separately they give two parsers, two toggles that can contradict each other, and a loop. So they are one feature with a direction.

2. What the other tools actually do

Read from the Sonarr, Radarr and Bazarr sources on 2026-10-15 (Sonarr and Radarr develop, Bazarr master). This section replaced guesswork in version 2 and changed two rules.

ToolWritesReadsRenames or deletes files it did not write
Sonarr, Radarr Video[.N].<iso2>[.tag...].ext. Language is always the two-letter code; pt-BR comes out as .pt. Tags are forced foreign default cc psdh sdh. The copy number sits before the language: Episode.1.en.srt. SubtitleService.cs GetSuffix Same tags. hi is not a tag; it is the code for Hindi, so Movie.en.hi.srt parses as Hindi with no tags. Movie.pt-BR.srt parses as unknown language. Movie.en.1.srt parses as English copy 1 through the title parser. LanguageParser.cs SubtitleLanguageRegex Yes. Every disk rescan imports any subtitle file beside a tracked video, not gated by "Import Extra Files" (ExistingExtraFileService, ExistingSubtitleImporter). On RenameFiles every tracked file is renamed, and the new name is rebuilt from the parsed fields, not copied from the old name (SubtitleService.MoveFilesAfterRename). So Movie.en.hi.srt becomes NewName.hi.srt (Hindi) and a pt-BR file loses its language segment. Tracked files go to the recycle bin when the video is upgraded.
Bazarr Video.<ietf>[.forced|.hi].ext. Language is the IETF tag: en, pt-BR, zh-TW. forced wins over the SDH tag, never both. The SDH tag is hi by default, configurable to cc or sdh. With "single language" on it writes a bare Video.srt. subliminal_patch/core.py get_subtitle_path, config.py hi_extension Strict: exactly one language code and at most one tag after the video name; a numbered file is ignored. Reads hi, cc, sdh as SDH. Content-detects the language of tagless files and SDH in untagged ones. Embedded tracks count as present by default (use_embedded_subs). core.py _search_external_subtitles, indexer/movies.py Never renames. Deletes only its own history entries on upgrade and on manual request. When a file it tracked disappears and the language is still wanted, it downloads again.
Consequences. (1) Muxarr must never write hi: the arrs read it as Hindi and rename accordingly. sdh is understood by all three tools. (2) Muxarr triggers a rescan and a rename itself after every conversion (#79), so any name Muxarr writes goes through the arr's parser and is rebuilt. Only names in the arr's own grammar survive that unchanged. (3) pt-BR cannot survive it. Bazarr wants it, the arrs cannot carry it. That is decision F below.

3. The model

What counts as a sidecar (reading)

Video[.N].<lang>[.sdh|.hi|.cc][.forced][.N].<srt|ass|ssa|vtt|sup>      beside Video.mkv, tags in any order

Video.en.srt              English
Video.pt-BR.srt           Portuguese (Brazil), as Bazarr writes it
Video.en.hi.srt           English SDH, as Bazarr writes it by default
Video.en.sdh.forced.srt   English, SDH, forced
Video.1.en.srt            English copy 1, as the arrs write it
Video.en.1.srt            the same, as PR #84 wrote it
Video.hi.srt              Hindi; "hi" is SDH only after a language

The language token has to match a known code, IETF tag or language name exactly; en-US and en-foo are not sidecars, since neither Bazarr nor the arrs write them and the general language lookup's "strip the region" fallback must not turn them into English. Each tag at most once, in any order, because the arrs preserve whatever order they parsed. The number is 1 to 99 and may sit on either side of the language. The file must be in the video's directory. Not a sidecar: Movie (2).en.srt, Movie.Part2.en.srt, Movie.en.2024.srt, a bare Movie.srt (decision A), Movie.und.srt. The scanner's ignore filter applies to sidecars too.

Proof: SubtitleSidecarTests, 41 cases, all pass. muxarr-tools sidecars <dir> run on Jesse's library on 2026-10-16: 1,944 videos, 1,873 sidecars parsed, 44 rejected, 0 ambiguous. Every parsed file is Dutch or English, with Sonarr-style numbered copies (.1.en, .2.en, .3.en) and two French ones. The rejected files are of three kinds: 37 bare Video.srt files with no language (decision A); 6 sidecars whose video has since been replaced by one with a different name (...x265.nl.srt beside ...x264.mp4), which is the orphan case rule 11 is about; and 1 beside a .ts file Muxarr does not handle.

What Muxarr writes

Video[.N].<iso2>[.sdh][.forced].ext        the arr grammar, so a rename round-trips

Movie.en.srt   Movie.en.sdh.srt   Movie.en.forced.srt   Movie.1.en.srt   Movie.pt.srt (see F)

Two-letter code, sdh never hi, the copy number before the language. ASS stays ASS; mov_text becomes SRT because it cannot exist as a file. No other conversion.

Where sidecars are stored

On MediaFile, as a JSON list, refreshed on every scan. Not in Snapshot.Tracks, not on the snapshot. Each entry holds the suffix, language, flags, format, size and modified time. The path is built from the video's path, so a rename keeps the list valid. Reasons, each checked in the code: a snapshot is rebuilt only when the video's size or time changes, so a sidecar in it would never be noticed; everything reading Snapshot.Tracks means container tracks (TrackCount, validator, structural check, mkvmerge and ffmpeg track ids, the unique index); Before and After snapshots are history; a JSON column goes through the existing value comparer so the scanner's save fires, as for IsHardlinked. Each sidecar gets a synthetic Index above any container index so it can flow through IMediaTrack code and the preview's dictionary.

Two kinds of subtitles

KindFormatsCan move
TextSRT, ASS/SSA, WebVTT, mov_textYes, both directions
ImagePGS, VobSub, DVB, .supNever

Note from the extractor check: ffmpeg 9 reports a WebVTT track inside Matroska as an unknown codec, so the scanner would not classify it and it would never be offered for extraction. mkvextract handles it fine. Environment limitation, not a design rule.

What the plan says

ConversionPlan.Tracks keeps its exact meaning: the output container, in order. The planner, Delta, the validator and both writers do not change. A sidecar being muxed in is in Tracks with a SourcePath. An extracted track is not in Tracks; it is in a second list, ExtractedSubtitles. A sidecar that stays as a file is not in the plan. Deletions are explicit actions attached to a move in the same plan. Every move changes the count or order of Tracks, so the structural check already answers Remux and the metadata-edit path can never run with a move pending. Delta must copy SourcePath and the extraction list through, which it does not today.

The profile setting

One choice in the Subtitles tab, with one switch under it, at the top level of the tab, outside the removal fold. A profile that filters nothing can still want every text subtitle as a file, and the fold is hidden when removal is off.

Text subtitles liveMeaning
Where they are (default)Current behaviour. Sidecars are shown in the library, nothing moves, and they take no part in the language rules.
Inside the fileA sidecar the profile keeps, not already embedded, is muxed in. MKV only; on MP4 and WebM this behaves as "Where they are" and flags nothing.
Next to the fileA kept embedded text subtitle with a known language is extracted and removed from the container. Any container.

Under it: Delete subtitle files Muxarr just moved, off by default.

4. How a plan is built

The insertion points sit before and after the language rules, never inside them. That is what keeps feature/advanced-settings untouched: its rewrite of GetAllowedTracks still receives a list of IMediaTrack and returns the kept ones.

1
Effective mode. "Inside the file" on a non-Matroska container, and any mode for an image sidecar, becomes "Where they are".
2
Candidates. In "Inside the file" the text sidecars join the embedded subtitles as candidates, except one whose language, forced flag, SDH flag and format already exist embedded on a non-commentary track (rule 3). In the other two modes the candidates are the embedded tracks only.
3
Language rules, unchanged. The undetermined-language resolution keeps counting embedded tracks only.
4
Split by destination. Kept embedded text subtitles in "Next to the file" go to the extraction list. Kept sidecars in "Inside the file" go to Tracks with a SourcePath. Everything else kept stays in Tracks. Sidecars not kept are not in the plan.
5
Mutations on container tracks only: flag correction, name standardization, default flag assignment and reordering. The split comes first so a sidecar cannot win the default flag. A muxed-in sidecar does get the standardized name, language tag and a position by priority.
6
Container quirks through TargetResolver as today.

Proof: SubtitleLocationModelProperties drives the real BuildTargetFromProfile with a simulated directory, 3,000 generated worlds per run, plus seed replay (MUXARR_PROP_REPLAY), three properties: deterministic; "Where they are" never moves or deletes and keeps exactly the plain profile's tracks; one conversion converges and loses nothing. The undetermined count in step 3 is the undeterminedCount parameter on GetAllowedTracks, the one place the rules are touched. Unit cases in SubtitleLocationTests, and the real tools in SubtitleLocationIntegrationTests: extraction from test_complex.mkv writes three files with cues and leaves no text track; a Dutch file beside test.mkv is muxed in and deleted with the switch on, kept and not muxed twice with it off.

5. Business rules

1
Keep or remove is decided by the profile, not by location. Language rules never delete files.
Proof: model property "Where they are", and the plain planner's own suite (865 tests).
2
Muxarr never removes a subtitle file it did not just move. With the switch on, the only files that go are the sidecar just muxed in and the like-for-like file an extracted one just replaced. "Removed" means moved to Muxarr's own bin, trash/subtitles beside the database, kept for 30 days. The plan records each file's size and time; a file that changed in between, say Bazarr upgraded it mid-conversion, is left alone and logged. A file whose subtitle is already inside the video is never removed: same language, flags and format do not prove the same text, and the switch's contract is "what Muxarr moved". Considered and rejected with Codex on 2026-10-16.
Proof: model property "loses nothing": with the switch off no file ever vanishes; with it on every deleted file is one a subtitle in the same plan replaced or vacated. The model found "same language and flags" too loose twice: it deleted an ASS beside a freshly extracted SRT, and then every numbered copy of the same subtitle. Rule 4 now names the one file.
3
Mux-in identity. A sidecar is muxed in only when no embedded non-commentary subtitle has the same language, forced flag, SDH flag and format. A commentary track is a different subtitle and cannot stand in for the file; the model found that it did, and the file was muxed in one conversion late. Without this, "Inside the file" with the delete switch off adds the same subtitle every conversion, because the language rules keep every track unless a limit is set.
Proof: model property "converges": the second pass has no moves, across all modes and switch states.
4
Extraction always extracts. If the name is taken: switch off, the new file is numbered (Movie.1.en.srt); switch on, the one file whose name the new one takes is replaced once the new one is in place. Numbered copies beside it are left alone, and an ASS beside an SRT is a different subtitle, not a double.
Proof: model property "loses nothing" and "converges". Cue conservation of the extractor itself: section 8.
5
"Where they are" is display only. Anyone upgrading with Bazarr files beside their videos sees the same plans as before.
Proof: model property, plus the plan dump in section 8 which will be the zero-diff check once the planner change exists.
6
Image subtitles never move, and "Inside the file" on MP4 or WebM moves nothing and flags nothing.
Proof: model property (image sidecars and MP4 worlds are generated and never move).
7
No name, no file. An embedded text subtitle with an unknown or undetermined language stays in the container in "Next to the file". A bare Video.srt is not a sidecar.
Proof: model property (undetermined tracks are generated and never extracted); parser tests reject the bare name.
8
Needs work. A fourth flag, HasMisplacedSubtitles, true when the plan contains an extraction or a mux-in. HasRedundantTracks stays about the container and becomes set based, and so does the converter's track-drop check that decides whether to measure track ends.
Proof: SubtitleLocationIntegrationTests flags the file in both directions and shows it clean after one conversion; SubtitleLocationModelProperties now runs the real planner.
9
Sidecars are read on every scan, outside the probe gate. A file whose sidecar set changed and now needs work is queued like a newly discovered file when scanned files are queued automatically.
Proof: ASidecarAppearing_FlagsTheFile_WithoutAProbe: a file dropped beside a scanned video flags it on the next scan and the snapshot id stays the same.
10
Order of operations. Extract to temp files and check each for events. Remux. Probe and validate. Swap the video. Place extracted sidecars under the video's name, before the rescan and the arr update, so the arr adopts them. Rescan. Let the arr rescan and rename. Reconcile (rule 11). Then run the deletions attached to the plan and remove the .muxbak backup. A failure before the swap leaves everything untouched. A failure after it keeps the temp sidecars on disk and logs loudly.
Proof: FinalizeFaultInjectionTests throw inside the converter at each of nine points, now with an extracting profile, and hash the directory. Every row leaves a playable video under its own name, and once the swap is committed every extracted subtitle is in place or still in its temp copy (section 8). Built as designed except for one point: the .muxbak backup is still removed right after the swap, as before, because the recovery sweeps are written around that; the muxed-in source files are deleted last, after post-processing. This exercises the handled-failure paths; a hard kill skips the rollback and is only covered by the startup recovery tests that already exist. The sidecar steps are not built, so their rows do not exist yet; the seam is in place to add them.
11
Renames follow the video. Muxarr writes arr-safe names, so when the arr renames the video it renames the sidecars to exactly the names Muxarr would expect. After the arr update, for every known sidecar: new name exists, adopt it; only the old name exists, move it; both exist, touch neither and log it.
Proof of today's behaviour: the fake-arr harness in /tmp/muxarr-e2e. Scenario 1 (arr renames video and sidecar): both renamed, Muxarr updates its path and never mentions the sidecar. Scenario 2 (video only): sidecar orphaned under the old name. Scenario 3 (arr dies after renaming the video): same as 2, and the conversion log shows no sign the arr died. Built as FollowRename. Rerun on the finished feature: with the arr renaming the sidecars, every extracted file ends up under the new name untouched by Muxarr; with the arr renaming the video only, Muxarr moves them; in the mux-in run the Dutch file went in and was deleted while the English one, already embedded, was left alone and moved along. The arr behaviour itself is from source reading, not yet reproduced against a real Sonarr or Radarr.
12
Naming on the way out is section 3's write grammar.
Proof: parser round-trips every written name (tests); the arr grammar is cited from source.
13
Empty tracks. An extracted file with no events is dropped and the track still leaves the container.
Proof: PR #84's HasEvents verified on four constructed empty tracks (BOM-only SRT, header-only ASS, empty mov_text), section 8.
14
The custom conversion window knows the files too. Files beside the video are listed unticked with a "file" badge; ticking one muxes it in. Every embedded text subtitle with a language has a "to file" toggle. "Apply profile" sets both the way the profile would. Batch edit stays metadata only. The names and source paths come from the same planner code the profile uses.
Proof: CustomConversionEditorTests (sidecar ticked gives a SourcePath, the toggle moves a track to the extraction list, "Apply profile" with "Next to the file" sets it), and a browser run on 2026-10-16: the Dutch file ticked and the English SDH track marked went through a real conversion, the container gained the Dutch track, Movie.en.sdh.srt appeared, and the conversion page listed both moves.

7. Decisions

QuestionDecision
ABare Video.srtNot a sidecar. Bazarr writes it only in "single language" mode and guesses the language from the content; Muxarr cannot. Documented limitation. Worth knowing: Jesse's own library has 37 of them, all beside Dutch shows or films, so this is not rare. If it matters later, the safe extension is "a bare file counts as the profile's first allowed language when the profile has exactly one", never a content guess.
BKept subtitle exists both embedded and as a file, "Next to the file"Extract and number; replace only with the delete switch on, and only like-for-like. Same language and flags are not proof of the same text.
CDelete switch defaultOff.
D"Inside the file" on MP4One hint line, no flag.
ESidecars after an arr renameWrite arr-safe names; place before the arr update; reconcile from disk afterwards. Never rely on the arr, never a blind rename.
FRegional variants: pt-BR as #83 asked, or pt as the arrs writeWrite the two-letter code (pt). Decided by Jesse on 2026-10-16. Muxarr's own post-conversion rename (#79) sends every sidecar through the arr, which cannot carry a region and would rebuild the name without the language. Bazarr may then treat the file as European Portuguese; that is Bazarr's limitation to live with. The #83 author should be told.

Defects found on master along the way

  1. A subtitle the user explicitly kept was removed on the second conversion. With "assume undetermined is original" on and "Undetermined" also in the allowed list, the filter kept the lone und track as Undetermined, but the mutation step still rewrote its language to the original language. After the write it carried a language the profile did not allow and went. Found by PlanConvergenceProperties. Fixed on 2026-10-16: ShouldResolveUndetermined now yields to an explicit Undetermined entry, which is the one check the filter and the mutation share. The property runs without exclusions since.
  2. Two conversions instead of one when a removal leaves exactly one undetermined track: the undetermined rule only fires then. The same applies to extraction: an untagged subtitle stays embedded (rule 7) until it is alone, then gets a language and a file on the next pass. By design, documented in both properties as the one allowed two-step case.
  3. The conversion log says nothing when the arr dies mid-rename (fake-arr scenario 3). Only the API client logs it.
  4. PR #84: mkvextract warnings (exit code 1) are not logged.
  5. A language could vanish entirely when "remove SDH" or "remove commentary" was combined with codec exclusion. FilterLanguage let any track of the language vouch for removing the SDH or commentary one, and only then applied codec exclusion, which could remove the voucher. English SDH SRT beside English PGS, with PGS excluded and SDH removal on: both went. Found through the location model (a sidecar dropped this way was muxed in a conversion late). Fixed on 2026-10-16: codec exclusion now runs first, so only a track that survives it can vouch. The model runs without the exclusion since.

Changes made while building

  • WebVTT files are shown but never muxed in: ffprobe 9 reports a muxed WebVTT track as an unknown codec, so the identity rule could not see it and would mux it again every time. Found in review.
  • Replace with the switch on is like-for-like by language, flags and format, so Bazarr's Movie.en.hi.srt is the file a new Movie.en.sdh.srt replaces, as the doubles table says. A free name is never overwritten: placement overwrites only the file the plan named.
  • The sidecar keeps the file name it was found under, so a lower-case movie.en.srt beside Movie.mkv still resolves on Linux.
  • A file is queued on a sidecar change only when that change is what needs work.
  • A muxed-in file's deletion looks for the old name first, so a clash left by rule 11 never deletes the wrong file.
  • The stored sidecar list is refreshed after the muxed sources are deleted, since that happens after the post-swap rescan.
  • A file is a merge candidate only when it is valid UTF-8 (mkvmerge assumes that) and holds at least one cue; the verdict is read once per file version. Two files with the same identity are not both merged; the lowest copy number wins.
  • One plan-level list of file removals, each with the file's size and time, replaced the per-track delete flag and the per-extraction replace name. Removals go to the bin and are refused when the file changed since the plan.

Seen in the browser

On 2026-10-16 the finished feature was driven through the UI on a scratch library: the profile summary badges, the segmented control with its hint and the delete switch appearing for the two moving modes, the library detail page listing the two files with the "file" tag and the preview showing three extraction arrows with the numbered name, the custom conversion window with the files unticked and the "to file" toggle, a custom conversion that muxed one file in and wrote one track out, the conversion detail page listing both moves, and a profile conversion on the show that muxed the Dutch file in and deleted it. One defect was found and fixed there: the sidecar's stored file name landed in the track name field.

9. Review record

Version 2 was traced by the author and reviewed independently by two further readers against master and feature/advanced-settings. Version 3 replaced reading with execution where it could: the arr and Bazarr behaviour comes from their sources with file and line references in the research notes, the rules above run as property tests, the finalize sequence has a failure matrix, and the extractor has cue counts. The tooling itself was then reviewed by Codex, which caught a false defect (the simulation claimed a faststart MP4 loses its layout on remux; the converter restores the source's value before calling ffmpeg, and the simulation now does too), the numbered-copy deletion in rule 4, the model writing numbers in the Bazarr position, and the parser's over-broad language lookup. Things in version 2 that were wrong and are fixed here: the write grammar (hi, number position, regional tags) and rule 4's replace scope.

The built feature was reviewed by Codex and by a second model independently. Both caught the conversion detail page's misplaced else and the WebVTT loop; between them also the overwrite on placement, the deletion order after a rename clash, a sidecar placement failure aborting the rest of the finalize sequence, and the missing failure-matrix rows. Rejected: that muxed-in files must not take part in default-flag assignment (they are container tracks afterwards, section 4 step 5), that the temp name pattern could overwrite user data, and the path escaping, which is the same as the existing input path.

10. The open PRs

PR #84 provides the extractor and most of the tests, and its cue conservation is verified. To land it has to adopt: the MediaFile sidecar list refreshed by the scanner; the single location setting plus the delete switch; the control outside the removal fold; the new flag; the arr-safe write grammar; placement before the rescan and arr update; no cleanup of temp sidecars after the swap; and logging of mkvextract warnings.

PR #45 is declined. Its mkvmerge multi-input code and SourcePath shape are reused when "Inside the file" is built on the same model.
